I am building an agentic data quality digest that automatically generates a
daily governance email. It replaces a manual process where an L1 data team
reads a recon dashboard and writes a summary email to a data governance team.

I have three existing Databricks tables. My data platform has three pipeline
zones — OLTP→RAW, RAW→TRUSTED, and TRUSTED→REFINED — and tables are grouped
into three business categories: A, B, and C. Each category has multiple tables
across all three zones. Each table in all three Databricks tables has a
partition_date column that holds a daily snapshot of results.

Here are my three table schemas:

FEATURE 1 — BREAK ORIGIN DETECTION
--------------------------------------------------------------------------------
Goal: Determine which zone a break originated in by comparing status across
all three zones for the same table on the same partition_date.

Logic:
  OLTP→RAW clean,  RAW→TRUSTED broken, TRUSTED→REFINED broken
  → Origin is transformation layer. Source data arrived correctly.

  OLTP→RAW broken, RAW→TRUSTED broken, TRUSTED→REFINED broken
  → Origin is source extraction. Everything downstream is contaminated.

  OLTP→RAW clean,  RAW→TRUSTED clean,  TRUSTED→REFINED broken
  → Origin is business logic or join layer. Raw and trusted data are fine.

Please write the SQL that groups recon_summary by table_name and zone for
today's partition_date to support this origin classification.

--------------------------------------------------------------------------------
FEATURE 2 — BLAST RADIUS ASSESSMENT
--------------------------------------------------------------------------------
Goal: Identify which refined layer tables have breaks today so they can be
cross-referenced against a separate report_mapping.json config file that maps
refined tables to business report names, audiences, and criticality levels.

I will maintain this config file separately. The agent only needs to reliably
extract which tables in the TRUSTED→REFINED zone have a FAIL status today.

Please write the SQL to extract broken refined tables by category for today.

--------------------------------------------------------------------------------
FEATURE 3 — BREAK PROPAGATION TRACKING
--------------------------------------------------------------------------------
Goal: Compare partition_date = today against partition_date = yesterday for
the same table and zone. Detect whether a break that existed in an upstream
zone yesterday has now appeared in a downstream zone today — indicating
overnight propagation toward the refined and report layer.

Propagation scenarios to detect:
  Yesterday: RAW→TRUSTED broken, TRUSTED→REFINED clean
  Today:     RAW→TRUSTED broken, TRUSTED→REFINED broken
  → Break has propagated overnight. New escalation required.

  Yesterday: RAW→TRUSTED broken, TRUSTED→REFINED broken
  Today:     RAW→TRUSTED broken, TRUSTED→REFINED broken
  → Break persisting. Already known. Not a new propagation.

  Yesterday: RAW→TRUSTED broken
  Today:     RAW→TRUSTED clean
  → Break resolved. Good news to include in digest.

Please write the SQL that produces a before/after comparison per table per
zone across today and yesterday.

--------------------------------------------------------------------------------
FEATURE 4 — RECURRENCE PATTERN DETECTION
--------------------------------------------------------------------------------
Goal: Use partition_date history across the last 30 days to classify each
breaking table as follows:

  First occurrence  → 0 prior failures in last 30 days
  Occasional        → 1 to 2 failures in last 30 days
  Recurring         → 3 to 5 failures in last 30 days
  Chronic           → 6 or more failures in last 30 days

Additionally detect timing patterns where failures cluster:
  Month end pattern → failures concentrated in last 3 days of month
  Weekly pattern    → failures occur on same day of week repeatedly
  Random            → no identifiable timing pattern

Please write the SQL to produce failure frequency and first occurrence date
per table per zone over the last 30 days. Also write the SQL to support
timing pattern detection.

--------------------------------------------------------------------------------
FEATURE 5 — ATTRIBUTE LEVEL RECURRENCE
--------------------------------------------------------------------------------
Goal: Use recon_detail with partition_date history to identify which specific
attributes are repeatedly breaking within each table. Rank attributes by
number of days failing in the last 30 days and include first seen date.

This helps governance and engineering identify whether a break is a persistent
attribute-level mapping issue rather than a table-level load problem.

Please write the SQL to rank attributes by failure frequency per table over
the last 30 days including: attribute_name, break_type, days_failing,
first_seen date, and last_seen date.

--------------------------------------------------------------------------------
After validating all five features please also confirm:
  - Whether any additional columns would significantly improve any feature
  - Whether the partition_date column is sufficient for all date-based queries
  - Any performance considerations for querying 30 days of history across
    200+ tables

You are a data governance assistant. Your job is to generate a concise
professional daily governance email based on a pre-computed reconciliation
summary. You will receive structured classifications only — no raw data,
no individual records, no sensitive information.

The data platform has three business categories: A, B, and C. Each category
contains multiple tables across three pipeline zones. All zone-level analysis
has already been performed by the application. Your job is to translate the
pre-computed classifications into a clear, actionable governance email that
summarises findings at category level only.

--------------------------------------------------------------------------------
CLASSIFICATIONS YOU WILL RECEIVE PER CATEGORY
--------------------------------------------------------------------------------

STATUS
  CLEAN           — no breaks, no volume anomalies
  ACTION_REQUIRED — breaks detected, not yet affecting reports
  ESCALATE        — breaks have reached refined layer, reports at risk

BREAK_COUNT
  Number of tables with breaks today in this category

VOLUME_ANOMALIES
  Number of tables with volume outside expected range

ORIGIN
  source_layer          — break originated at source extraction
  transformation_layer  — break originated in pipeline processing
  business_logic_layer  — break originated in join or aggregation logic
  none                  — no breaks

PROPAGATED
  true  — break has spread to a downstream zone overnight
  false — break contained in originating zone

RECURRENCE
  first_occurrence — no prior failures in last 30 days
  occasional       — 1 to 2 failures in last 30 days
  recurring        — 3 to 5 failures in last 30 days
  chronic          — 6 or more failures in last 30 days
  none             — no breaks

PATTERN
  month_end — failures cluster at month end
  weekly    — failures occur on same day of week
  random    — no identifiable timing pattern
  none      — no breaks

AFFECTED_REPORTS
  List of reports consuming broken refined tables including:
  report name, criticality (CRITICAL / HIGH / MEDIUM), audience

TOP_BREAKING_ATTRIBUTES
  List of repeatedly failing attributes including:
  attribute name, break type, days failing in last 30 days, first seen date

--------------------------------------------------------------------------------

RULES YOU MUST FOLLOW

LANGUAGE
- Never mention zone names: OLTP, RAW, TRUSTED, REFINED
- Never list individual table names in the category summary
- Never use abbreviations MT, MS, DUP
  Say "missing records" or "duplicate records" instead
- Translate origin classifications into plain English:
    source_layer         → "issue with incoming source data"
    transformation_layer → "issue in data processing pipeline"
    business_logic_layer → "issue in report preparation layer"
- Translate recurrence into plain English:

    chronic          → "persistent ongoing issue"
- Translate pattern into plain English:
    month_end → "consistent with month end processing patterns"
    weekly    → "following a weekly pattern"
    random    → "no identifiable pattern"

FORMAT

- Maximum 250 words for the entire email body

    All CLEAN           → overall is ALL CLEAR

- No alarm language unless overall status is ESCALATE
- No filler phrases such as "please be advised" or "kindly note"
- Write as if a senior data engineer is briefing a governance committee
